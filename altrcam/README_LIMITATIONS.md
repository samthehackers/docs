# Limitations & honest status

## Not verified against real services
This was built in a sandbox with no network access to fal.ai, Clerk, Supabase, Paystack, NOWPayments, Resend or Upstash. What that means concretely:

- **fal WebRTC signaling is unverified (highest risk).** `lib/fal/signaling.ts` sends an SDP offer over fal's realtime socket (`@fal-ai/client`), applies the answer, trickles ICE candidates and plays the remote track. The message names/fields (`offer`, `answer`, `ice_candidate`, `ice_servers`, `error`, and the offer's `prompt` / `enable_prompt_expansion` / `reference_image_url`) are my best reading, **not fal's published schema**. Serialization is the `@fal-ai/client` default (what fal's documented `fal.realtime.connect(...).send(obj)` usage relies on); whether the endpoint expects that or JSON text frames is also unverified. Nothing in the Studio has been run against the live model. Treat the first real session as the integration test. The details below say exactly what a fake does and does not prove.
  - **Correction: message order mattered too, not only the names.** An earlier version of this file said that if fal differs, only the `Outgoing` / `Incoming` types and `handleIncoming` would need changing. That was wrong. Driving the real pinned client (`@fal-ai/client` 1.10.1, `src/realtime.js`) with a fake WebSocket showed two properties of it that the first version of our code violated: **(a)** the client opens nothing until the first `send()` (no token request, no socket), so waiting for a server-first message (`ice_servers`) before sending can never succeed; the old code always fell through to its 3 s timer. **(b)** until the socket is open the client keeps a *single* pending message and a later `send()` replaces it, so trickled ICE candidates replaced the offer. Against a fake WebSocket (what the committed tests use) the old code put only `ice_candidate` frames on the wire and never the offer. (The author also saw this in a throwaway browser harness that is not committed, so treat the committed tests as the evidence.)
  - **What the code does now, whatever the names turn out to be:** it sends the offer first, never waits for a server message, holds every later outgoing message (the ICE candidates) in its own ordered queue, and flushes that queue in order once the server's *first reply of any type* has arrived (a reply can only arrive once the socket is open). Names and shapes are unchanged.
  - **Proven by fakes** (`tests/unit/signaling-real-client.test.ts` runs our code through the *real* client with only `WebSocket`, `fetch` and `RTCPeerConnection` faked; `tests/unit/signaling.test.ts` covers lifecycle with the client mocked): the client facts above; offer first with no server message and no timer; candidates held until the first reply and then flushed in order, even if the reply's type is unknown; nothing sent after `close()` (a late send would make the client open a fresh socket); a refused or unreachable token request reported at once with its HTTP status; a failure is final, keeps its reason and is not followed by "closed"; every timer and peer callback released on every exit path. **Not proven:** that the real service replies at all, replies in this order or shape, accepts the offer fields, or accepts the token request our proxy forwards; whether it answers only after it has *some* candidates (then the answer would never come and the Studio would report "didn't answer"); how real networks, browsers and WebSocket handshakes behave. The fakes were written by the same person who wrote the code, from reading the client's source.
  - **ICE servers from the service are not used.** Nothing can reach us before our first send, so the offer is made with the public STUN server `stun:stun.l.google.com:19302` (it was the fallback before too) and a later `ice_servers` message is ignored. If the real service requires its own TURN servers, users on restrictive networks will fail with "couldn't set up a direct video connection", and the flow needs a different first message that opens the socket, then waits for `ice_servers`. That cannot be decided without the real service.
  - **The connection-token request is ours, not the client's.** The pinned client swallows a failed token request (it goes quiet; `onError` is never called), which looked like a 20 s "model didn't answer". `connectLucy` now passes its own `tokenProvider` that makes the same request (`POST /api/fal/proxy`, `x-fal-target-url: https://rest.fal.ai/tokens/`, `allowed_apps: ["lucy-2-5"]`, 120 s) and reports the status. It accepts a JSON string, plain text or `{ detail }` as the token. It sets no `tokenExpirationSeconds`, so the client schedules no token-refresh timer (the client never clears one when the socket closes before it opens, and an open socket does not need a fresh token as far as the client's code shows). What fal's token endpoint really returns is unverified.
  - **Known limits of the pinned client, not worked around.** Reproduced with the fake socket (a test records it, so an upgrade that changes it shows up): closing while the WebSocket handshake is still in flight does not close that socket (the client only closes a socket it has seen open), so a Stop or a failed attempt in that window leaves one orphan socket until the service drops it. The window lasts as long as the handshake hangs, which is the stuck-"Connecting" case. What is worked around: the client keeps one pending message for a socket that is still opening, so `release()` overwrites our offer with an empty message when the service has not replied, and the orphan then sends `{}` instead of delivering the offer (prompt and SDP) to a dead session (tested against the real client). The orphan socket itself, and whatever the service does with an empty first message, are untested against the real service. Read from the client's source, not tested: a server `Unauthorized` message is swallowed and would surface only as the 20 s "didn't answer" failure; the client keeps a small per-connection cache entry for the life of the page. **Not decided, because it depends on how fal behaves:** a non-normal close of the signaling socket while video is flowing (code 1006, say) is treated as fatal and tears the session down; and if the service closes that socket normally, the next local ICE candidate makes the client open a second socket carrying only that candidate. Both were reproduced with fakes and are not covered by a rule yet; decide them from the first real run.
  - **Unverified background facts, recorded for whoever runs the first real session.** None of these was read from fal's or Decart's documentation, and **no message name, field or option in the code was changed because of them.** (1) From public search-result snippets of fal's own realtime example: it calls `fal.realtime.connect` with `onResult`, `onError` and a `tokenProvider` that POSTs to the app's backend and returns the token as plain text, uses `tokenExpirationSeconds` of 10, and ends with `connection.send({})`. (2) From the same kind of snippet of fal's guide: about $0.04 per second of processed video (also under pricing below). (3) From public snippets about Decart's own non-fal API: it uses an `ice-candidate` message type and an `answer` type carrying `sdp`. If the first real session shows our names are wrong, these are leads, not answers.
- The Clerk, Supabase Storage (signed-upload via `PUT` multipart), Resend and Upstash paths compile and are unit-tested only where they touch our own logic. They have not been run end to end.
- The Playwright sign-up → pay → unlock e2e (`tests/e2e`) is written but **has not been executed** (it needs a Clerk dev instance and Postgres). What *has* run: unit and isolation tests against a real in-memory Postgres, typecheck, lint, a no-credential `next build`, and a credential-free Playwright suite (`npm run test:public`) in real Chromium covering responsive layout, accessibility basics, security headers and honest failure modes.
- **Provider pricing is unverified.** A search summary put Lucy realtime at roughly $0.04 per processed second; I could not open fal's pricing page. At that rate the default allowances (300 free / 6,000 Pro credits per month) would cost far more than any normal price. Confirm real pricing before setting allowances (Admin → Plans) or prices. See `GO_LIVE.md` section 1.
- Paystack `GET /transaction/verify` and NOWPayments `GET /payment/:id` response shapes follow their public docs from memory; confirm in test mode.

## What the Lucy realtime API can and cannot do here
- **No microphone.** The Studio requests the camera only, and says so on the page ("AltrCam transforms video only..."). Lucy's documented inputs are video plus a prompt (and optional reference image), and I couldn't confirm that audio is accepted or passed through, so there is no mic control and no audio is captured or sent. Adding it is **not** a one-line change: besides the `getUserMedia` audio constraint it needs the `microphone=()` Permissions-Policy in `next.config.ts` relaxed, a microphone picker and mute control, handling for a remote audio track, and updated privacy wording. Do that only once the API's audio behavior is confirmed.
- Inputs exposed in the UI: `prompt`, `enable_prompt_expansion`, `reference_image_url`. There is **no** control for anything else. `image_url` is not exposed because its semantics aren't confirmed.
- Inputs are sent with the offer. "Apply changes" therefore **re-negotiates the stream** (brief interruption) rather than changing the prompt mid-stream. Whether the model supports live prompt updates is unknown.
- "Resolution" on the plan limits the **camera capture** size (640×360 vs 1280×720). Output resolution/FPS is decided by the model.
- Background swap, outfit and style are prompt (± reference image) presets, not separate model features.
- The fal realtime socket connects **directly** to fal using a short-lived token. Our proxy can only gate the token mint (and refresh), not the media. It mints a token only for the caller's own open session that has heartbeated within 30 s and is either live or still inside its 30 s connect window, with a lifetime of at most 120 s (what the Studio asks for; it used to accept up to 300). A tampered client that ignores `continue:false` could keep an already-open connection for as long as fal lets it (see "Live is reported by the browser" below). Server-side billing still stops at zero credits and the stale sweep closes the session record.

## Studio behaviour when things go wrong
What the page does now. It is unit-tested with fakes (`tests/unit/studio-session.test.ts`, `studio-camera.test.ts`, `studio-messages.test.ts`, `studio-component.test.ts`) and was driven once in Chromium with a fake camera against a faked server by its author, a manual harness that is **not** committed and not part of the test suite (so nothing here should be relied on because of it). None of it has been seen against the real service, real Clerk, or other browsers and real cameras.

- **A failed connection ends its server session.** When the connection fails (connection token refused or unreachable, socket error, the service's own error message, no answer in 20 s, a browser-side ICE failure, an unusable answer, or a disconnect that does not recover in 15 s) the page stops its timers and heartbeats, closes the connection, calls `/api/studio/session/end` with reason `connection_failed`, and keeps the reason on screen with a Reconnect button until the user acts. If the end call cannot be made (for example offline), the page says so and retries it when the browser comes back online or at unmount; otherwise the stale sweep, or the next session start, closes it, billed up to the last heartbeat.
- **Billing starts at the first transformed frame.** A session is created "connecting" with no debit. When the output video renders its first frame (`requestVideoFrameCallback`, with `loadeddata`/`playing` as fallback and safety net, `lib/first-frame.ts`) the page calls `POST /api/studio/session/live`, and the server records `live_at` from its own clock, once. Heartbeats, the end call, a superseding start and the stale sweep all bill whole seconds from `live_at` only; a session that never reached it is closed with 0 credits. Time spent connecting, and the "Reconnecting…" grace before a dropped connection is given up, are free before the first frame; after it, a reconnecting session is still live and still billed (it is the same session). "Live" is reported by the browser, so a tampered client could stream without reporting it: see "Billing & product gaps" below.
- **Reconnect is a new session.** It ends the failed or stuck session and starts a new one, billed from its own first frame, and the page says so. **There is no automatic retry, on purpose:** each attempt is a new billed session, and until a first real run shows what fails, retrying on its own could spend credits on attempts that fail the same way every time.
- **Admin end reasons.** Sessions ended by the browser now carry `user`, `connection_failed`, `camera_lost` or `reconnect` in `studio_sessions.end_reason` (Admin lists it). The end route accepts only those four from a browser. A run of `connection_failed` in Admin after launch is the signal that signaling is not working.
- **A Stop the server didn't hear about.** If the end call fails (offline, or a 5xx), the page shows "We couldn't reach the server to close the session" and retries once when the browser comes back online or at unmount. A 5xx while still online is **not** retried by a timer, and a tab closed in that state does not re-send it. The session is then closed by the stale sweep (billed up to the last heartbeat) or when the user next goes live.
- **Offline.** The page watches `navigator.onLine` and the browser's online/offline events. `onLine` can say "online" without working internet, so it only shows a banner and refuses to start when the browser says it is offline; real failures are still reported by the requests themselves.
- **Camera.** Separate messages for blocked, no camera, in use by another app, not available at the requested size, unplugged mid-session, and insecure (non-https) pages, with a Retry camera button. A failed camera switch clears the stream and the preview, so "Go live" cannot start with a dead stream. If the live video track ends, the session is ended (`camera_lost`). The camera list refreshes on `devicechange`. The error names are mapped from the spec and from memory and were not tried in every browser; the mid-session "track ended" case was simulated with a synthetic event, not an unplugged device.
- **Start errors.** Out of credits (402), rate limit (429), unavailable (503, showing the server's own "not available yet" message) and network failures each have a message; everything except 402 and sign-in problems offers Try again.

## Account pages (dashboard, history, support)
- `/dashboard` reads only our own database and has been rendered only in unit tests against an in-memory Postgres, never in a browser with real sign-in. The plan status ("Active", "Cancelled", "Payment failed", "Pro ended"), renewal date and last payment come from `users.plan_status`, `users.plan_renews_at` and `payments`, which the payment webhooks write; those webhooks have never run against real Paystack (above). "Renews" is only shown when an active subscription row exists, the same rule as the Billing page.
- The "used this month" meter counts this calendar month's (UTC) session debits from the monthly bucket against the plan's current allowance. It measures spending, not the balance, so after a mid-month plan change the meter and the monthly balance can differ. A plan whose monthly allowance is 0 gets a sentence instead of a meter.
- `/history` lists manual snapshots only. A session without a Snapshot leaves no row there; sessions are listed on the dashboard (newest 8, prompt cut to 120 characters). Clips are downloaded to the user's device and never stored.
- The troubleshooting answers on `/support` were written from reading the code, the FAQ and the Terms, not from watching real sessions. They promise no response time and no refund. The Studio status words they explain (Ready, Connecting, Live, Failed, Closed) come from `components/studio/studio.tsx`; re-read them if that file's wording changes.

## Billing & product gaps
- **"Live" is reported by the browser (residual risk).** Billing starts when the page calls `POST /api/studio/session/live`, so a modified client could stream transformed video without ever calling it and pay nothing. What limits that: (1) a session that has not gone live within 30 s is closed as `failed_connect` by its next heartbeat, end call, the next start or the sweep, and `/live` is refused after that; (2) the fal proxy mints connection tokens only while a session is live or inside those first 30 s, and only while it keeps heartbeating, each token living at most 120 s; (3) Go live is refused (HTTP 429, `connect_cooldown`) while more than 5 of the user's sessions started in the last 10 minutes ended without going live, whatever ended them, including the browser's own Stop. 5 allows two failed Go lives with their automatic retry plus one more before the pause, which lifts by itself as the oldest attempt leaves the window; plus the existing limit of 10 starts a minute. **Not verified, and decisive:** whether fal ends a connection that is already open when its token expires. If it does not, one token is enough to stream for as long as the socket stays up, unbilled, and these limits only cap how often that can be started. Compare fal's own usage report with what the app billed (sum of `seconds_billed`, or of `session` debits in `credit_ledger`) after launch, and alert on a gap; `studio_sessions` rows with `live_at` empty and a long gap between `started_at` and `ended_at` are the place to look.
- Stale sessions are billed to the last heartbeat, so a user who kills the tab right before a heartbeat can get up to ~10 s unbilled per session.
- A session abandoned without a clean close (crash, network loss) stays open until the stale sweep closes it or the user starts a new session. Starting a new session closes a silent one exactly as the sweep would, billed only up to its last heartbeat, so the bill does not depend on whether the sweep ran. Until one of those happens the session can still mint fal tokens. There is no dead-man's switch: nothing alerts you if the sweep stops running.
- Deliberate trade-off: billing is by the server clock, not by heartbeat gaps. If the *same* tab comes back (computer sleep, then wake) and sends a heartbeat before anything has closed the session, the silence is billed, up to the plan's max session length. Billing only the time between heartbeats would let a modified client stream while heartbeating rarely, so this stays until there is a safer way to tell a sleeping tab from a streaming one.
- "Receipts" are an email plus the payment reference in Billing. There are no PDF invoices.
- Crypto has no recurring billing; it is offered for Lifetime and top-ups. NOWPayments fiat price currency support (e.g. NGN) depends on your account; USD is the safe choice.
- Paystack renewals arrive as `charge.success` with no pending row; they are resolved by plan code → product and the customer's email → user. The Paystack plan amount must equal `PRICE_PRO_*` or renewals are recorded as `rejected`.
- Downgrade is "cancel at period end"; there is no proration or in-place plan switching (monthly ↔ yearly is a new checkout).
- **Lifetime bought on top of a Pro subscription:** buying Lifetime cancels the active subscription at the provider (Paystack) after the purchase commits. If that call fails, the purchase still stands, a `subscription.cancel_failed` audit entry is written and the user is asked to cancel via the provider's email link. A Pro charge that still arrives after Lifetime does not change the plan or credits; it is recorded as paid and flagged `payment.after_lifetime` in the audit log, and the user is told to contact support. **Refunding it is manual**, like every other refund.
- **Refunds and chargebacks are not handled for any purchase.** The app does not listen for Paystack refund/dispute events or NOWPayments refunds. Credits and plans stay granted until an admin revokes them by hand (Admin → Users). Referral rewards are likewise paid immediately and are **not clawed back** if the friend's payment is later refunded.
- **Referrals:** the referrer gets 600 credits (purchased bucket, never expire) when an invited friend first pays for Pro or Lifetime, capped at 20 rewarded friends per referrer. The friend must sign up after clicking the link and be claimed within a day of signing up; the first link clicked wins; mutual and longer referral rings are rejected; top-ups don't count. It does **not** stop one person running several accounts: that costs them a real Pro/Lifetime payment per account, so the reward is smaller than what they paid, but it is not prevented. If the reward step ever fails, the payment is kept and a `referral.reward_failed` audit entry is written for manual reconciliation.
- Rate limiting is a no-op in development when Upstash isn't configured; in production a missing limiter errors loudly.
- The CSP allows `'unsafe-inline'` scripts (Clerk and Next inline bootstraps). Tightening to nonces is future work.
- Unauthenticated requests to protected pages return Clerk's default (redirect to sign-in in a browser; 404 for non-HTML clients).

## What the public pages say
- The landing page, `/how-it-works`, `/pricing`, the FAQ and `/billing` say that live video **has not been tested end to end** and **may not connect**, and that "Credits count only while your transformed video is live. If it never connects, you pay nothing." (`CREDITS_RULE`, also used by how-it-works step 4, the landing tile, the FAQ, the pricing billing details, troubleshooting and the Studio; the Terms say the same in their own words). One wording (`lib/availability.ts`). The meta description and hero say the product is "built to" restyle video, not that it does. Change this only after a real session has been run (GO_LIVE.md, section 7).
- They also state, from what the code does: the camera preview stays in the browser; video goes to a third-party AI service only after Go live; a reference image is uploaded to our storage when picked and sent to the AI service as a signed link; video only, no audio (tests tie this to `audio: false` in the camera code); snapshots are saved to History on every plan; **clips are downloaded to the user's device and never stored by us** (the upload route accepts them but nothing calls it); clip availability per plan is read from the plan config.
- `/pricing` has a "Billing details" list (renewal, cancelling, currency, payment methods, top-ups, Lifetime, refund position). It mirrors checkout, the webhooks and the Terms; the Terms themselves are still template text. Which Paystack payment methods apply to a subscription is Paystack's decision and is not claimed. Crypto amounts are quoted by NOWPayments at checkout. "Lifetime" is not defined anywhere in the Terms yet, and the page says so.
- "Resolution" on pricing cards is worded as the **camera size the Studio requests** (`CAPTURE_SIZE` in `lib/plans.ts`, now also used by the Studio). The browser treats it as a request, so the camera may deliver something else, and the AI service decides what it returns.
- Rendering: with Clerk configured every marketing page is dynamic (the layout reads the session), so `revalidate = 60` is moot there and admin plan changes show within the plan-config cache time (about 15 s). With no Clerk the pages are static and revalidate every minute.
- **History retention for Lifetime is not enforced if an admin sets it.** The daily retention job only purges FREE and PRO plans; a Lifetime `historyDays` set in Admin would be shown on the pricing card and never applied. The default (no expiry) is accurate.
- The footer says "Powered by Lucy 2.5 from Decart" on every public page, including the ones that say live video is untested. It is the attribution the owner asked for; nobody has checked it against Decart's or fal's terms.
- The pages have been checked by rendering them in unit tests and in the credential-free browser suite. They have not been reviewed by a lawyer.
